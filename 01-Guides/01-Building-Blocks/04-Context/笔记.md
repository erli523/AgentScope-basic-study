# 04 Context — 学习笔记

## 1. 一句话

**Context = Agent 的工作记忆**：模型每一步推理时真正「看见」的内容。

乍看材料不算特别多，但和 Agent 章节是连着的：`context_config` 本身就是创建 Agent 时的一个**可选项**。

## 2. 一次模型调用看到的三层

每次调用前，智能体把三层拼成单次 API 输入：

```text
Model Input
├─ System Prompt
│    ├─ 基础 system_prompt
│    ├─ skill 指令（来自 Toolkit）
│    └─ on_system_prompt 中间件钩子
├─ Summary（可选）
│    └─ 较早消息被压缩后的摘要；只有发生过压缩才有
└─ Context
     └─ 最近尚未压缩的消息（用户 / assistant / tool_call / tool_result）
```

- 没压缩时 Summary 为空  
- 压缩后：旧消息 → summary，新消息留在 context  

`AgentState` 里也会体现这一点：`session_id`、`summary`、未压缩的 `context` 等。每个会话、每个 Agent 维护一份独立状态。

## 3. 三种机制（核心）

上下文管理主要就这三块：

### 3.1 上下文压缩

当 token 用量逼近模型上限时，把较早消息汇总成摘要。

- 可在推理前**自动**执行，也可手动 `await agent.compress_context()`
- 典型步骤：
  1. 计算 token  
  2. 判断是否超过 `trigger_ratio * context_size`  
  3. 切分消息：较早的压缩，近期的保留（工具调用/结果尽量成对）  
  4. 生成结构化摘要，写回 `summary`

配置示例：

```python
context_config = ContextConfig(
    trigger_ratio=0.8,
    reserve_ratio=0.1,
    tool_result_limit=3000,
)
```

### 3.2 工具结果截断

过大的工具输出在进入上下文之前先截断。

- 由 `tool_result_limit` 控制  
- 保留部分会追加截断标记（如 `<<<TRUNCATED>>>`），让智能体知道输出不完整  

### 3.3 上下文 Offload

把**已经从上下文中移除**的内容持久化到外部存储，方便之后用文件工具（Read / Grep / Glob）回查。

两类方法有区别：

| 方法 | 何时用 |
|------|--------|
| `offload_context(session_id, msgs)` | 压缩时：把被移出的旧消息写出去 |
| `offload_tool_result(session_id, tool_result)` | 工具结果过长被截断时：把截掉的部分写出去 |

注意：截断时**不是悄悄丢掉就完了**——上下文里会留提醒；若挂了 offloader，还可以指向落盘路径。

需要接数据库 / 对象存储 / 向量库时，实现 Offloader 协议即可（结构化协议，不必继承），这一点比较方便。

## 4. 不要和这些混淆

| 概念 | 管什么 |
|------|--------|
| **Context** | 此刻窗口里有什么 |
| **Session** | 这份状态存哪里、怎么恢复 |
| **RAG** | 外部知识怎么检索注入 |
| **Long-Term Memory** | 跨会话记住什么（应受控） |

压缩和 offload 仍属于短期 / 会话内机制，**不等于**跨会话长期记忆。
