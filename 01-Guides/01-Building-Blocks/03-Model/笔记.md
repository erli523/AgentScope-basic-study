# 03 Model — 学习笔记

## 1. 为什么还需要 Model 抽象

不同供应商的请求字段、流式协议、工具调用格式和 usage 返回值并不完全相同。  
AgentScope Model 的作用，是把这些差异收成统一接口：

- 输入：AgentScope `Msg`
- 输出：`ChatResponse`（或流式的一串 `ChatResponse`）

```python
raw = await model([SystemMsg(...), UserMsg(...)])
```

## 2. Credential、模型族、具体模型

模型层可以分成：

| 概念 | 管什么 |
|------|--------|
| **Credential** | 如何访问模型平台（API Key、base_url 等） |
| **模型族** | 调用哪一种能力（LLM / TTS / Embedding / Realtime…） |
| **具体模型** | 最终用哪个模型名 |

一个 Credential 对应一个 API（如 OpenAI、Gemini、DashScope），再对应到该 API 下的若干模型族。

构造示例（平时多数情况只用前几项）：

```python
model = DashScopeChatModel(
    credential=...,
    model=...,
    stream=True,
    parameters=...,   # 看供应商是否需要
    max_retries=...,
    formatter=...,    # 覆盖默认消息 formatter；一般较少碰
)
```

**Formatter：** 负责把 AgentScope 的 `Msg` 转成各提供商期望的 `list[dict]`。  
通过构造函数可选的 `formatter` 传入；每个提供商通常内置自己的 formatter。  
感觉日常开发里不太会深入改它，知道「配置 model 时可以传」即可。  
TTS / 多模态等暂时用得少，先跳过也没关系。

## 3. Credential / Model / Agent 的边界

| 层 | 负责 | 不负责 |
|----|------|--------|
| Credential | API Key、base URL 等认证 | Prompt、工具执行、会话历史 |
| Model | 单次模型请求、格式转换、重试、流式 chunk | 完整 ReAct 循环、工具真实执行 |
| Agent | 上下文、模型、工具、推理—行动循环 | 供应商底层 HTTP 协议 |

不要把 Credential 当普通字典打印。Demo 只展示供应商、模型名和 base URL，不输出 Key。

## 4. `model(messages)` 在干什么

`__call__` 是 Python 魔法方法：让对象可以像函数一样调用。

```python
model = DashScopeChatModel(...)          # 先得到模型对象（还没请求）
result = await model(messages)           # 等价于 await model.__call__(messages)
```

签名大致是：

```python
async def __call__(
    self,
    messages: list[Msg],
    tools: list[dict] | None = None,
    tool_choice: ToolChoice | None = None,
    **kwargs: Any,
) -> ChatResponse | AsyncGenerator[ChatResponse, None]:
```

返回值怎么理解：

| `stream` | 返回什么 |
|----------|----------|
| `False` | 一个完整的 `ChatResponse` |
| `True` | 异步生成器，里面一个个吐出 `ChatResponse` chunk |

一句话：`model(messages)` = 请这个已配置好的大模型，根据这些消息**生成一次**回复。

## 5. 和 `agent.reply` 的关系（这章为什么突然直调 Model）

| 场景 | 用什么 |
|------|--------|
| 聊天助手、要工具、要多轮、要事件流 | `agent.reply` / `reply_stream` |
| 测某个模型、调温度、看 token、学结构化输出 | 直接 `model(messages)` |
| 生产里多数业务逻辑 | 仍挂在 Agent 上，Model 只是组件 |

可以记成：

> 1、2 章学怎么开飞机（Agent）；3 章学发动机单独怎么转（Model）。  
> 飞机还是靠 `reply` 飞，只是这章把发动机拆下来给你看。

理解上可以确认：

**`agent.reply` 里面封装了对 `model(messages, tools=...)` 的调用。**

但不是「一次 reply = 只调一次 model」：

```text
agent.reply(用户消息)
  ├─ 第 1 次 model(messages, tools=...)   # 可能返回 tool_call
  ├─ 执行工具，把 tool_result 塞进上下文
  ├─ 第 2 次 model(messages, tools=...)   # 再推理
  └─ …直到给出最终文本或达到 max_iters
```

所以更准确：

- `model(messages)`：一次模型 API 调用  
- `agent.reply`：封装了「多次 `model(...)` + 工具 + 上下文 + 事件」的整轮循环  

## 6. ChatResponse 与 Agent Event

- Model 流 → `ChatResponse` chunk（更接近一次模型 API 结果）
- Agent 流 → `AgentEvent`（覆盖模型、工具、权限、最终回复等）

流式 Model 里：

- 普通 chunk：增量  
- 最后一个 `is_last=True`：通常是聚合后的完整结果  

因此不能把所有增量和最终聚合文本再加一遍，否则会重复。

## 7. 模型参数与 usage

常用参数：

- `temperature`：采样随机程度，不是「事实正确率」开关  
- `max_tokens`：限制最大**输出**，不等于上下文窗口  
- `top_p`：另一种采样控制；初学不要和 temperature 一起猛调  
- `thinking_enable` / `reasoning_effort`：仅部分模型/供应商支持  
- `parallel_tool_calls`：是否允许一次生成多个工具调用  
- `context_size`：客户端配置的最大上下文容量  

生产中应为具体模型验证配置，不要假定同名参数在所有供应商上行为一致。

`usage` 适合用来做成本估算、上下文增长告警、Prompt/模型对比、容量规划。  
兼容服务不一定都返回同样字段，代码应允许其为 `None`。

## 8. 工具调用：Model 只「生成调用」，不「执行工具」

给 Model 的是工具 JSON Schema。它返回 `ToolCallBlock`（工具名 + 参数字符串），但此时：

- 权限未必已检查  
- Python 工具函数未必已执行  
- 工具结果未必已回填  
- 也未必已基于结果生成最终回答  

这些通常由 `Agent + Toolkit` 完成。所以 `05_model_tool_call.py` 只观察 ToolCallBlock，不真正执行工具。

## 9. 结构化输出

需要符合 Pydantic / JSON Schema 的结果时，用 `generate_structured_output`，而不是普通 `__call__`。  
它返回 `StructuredResponse`，`content` 一般是经过 schema 约束的 dict。

仍需要：

- Pydantic 字段与范围校验（如 `model_validate`）
- 业务规则校验  
- 处理缺失字段、供应商不兼容、解析失败  
- 不能因为是 JSON 就自动信任业务事实  

导出时可用 `model_dump()` 把对象变回 dict，方便打印或落库。

## 10. 供应商切换

上层应依赖统一的模型构建函数，不要在 Agent 里散落供应商判断。切换时至少验证：

1. 模型是否存在且 Key 有权限  
2. 流式响应格式  
3. 工具调用支持  
4. 结构化输出支持  
5. 上下文窗口与 token 计费  
6. 超时、限流和重试  

「兼容 OpenAI API」只说明 HTTP 形状相近，不保证所有能力都一致。

---

目前感觉：本章真正常用的是 Credential / ChatModel / 直调与流式 / 和 Agent 的边界；TTS、多模态等可以后补。
