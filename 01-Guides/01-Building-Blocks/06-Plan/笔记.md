# 06 Plan（计划模式）— 学习笔记

## 1. 计划模式是什么

不是让模型随意探索，而是**维持一份显式的任务清单**，边拆解边推进。

四个内置工具：

| 工具 | 作用 |
|------|------|
| `TaskCreate` | 向任务清单尾部增加新任务 |
| `TaskGet` | 按 id 获取单个任务的完整信息 |
| `TaskList` | 列出所有任务、状态、owner、阻塞关系 |
| `TaskUpdate` | 更新任务字段 / 状态，也可删除 |

四者都是**状态注入式工具**（`is_state_injected=True`）：运行时把当前 `AgentState` 注入每次调用，工具直接读写 `agent.state.tasks_context`。

接入方式：

```python
from agentscope.tool import Toolkit, TaskCreate, TaskGet, TaskList, TaskUpdate

toolkit = Toolkit(
    tools=[
        TaskCreate(),
        TaskGet(),
        TaskList(),
        TaskUpdate(),
    ],
)

agent = Agent(
    name="...",
    system_prompt="...",
    model=...,
    toolkit=toolkit,
    # 注意：Agent 没有 description 这个构造参数
)
```

权限上：计划工具的 `check_permissions()` **硬编码为 ALLOW**——它们只改内存里的任务状态，一般不会因此弹出用户确认。

## 2. 自己理解的典型循环

1. 把复杂指令拆成一系列任务 → `TaskCreate`（初始多为 `pending`）  
2. 用 `TaskList` 找「id 最小且未被阻塞」的下一个任务  
3. `TaskUpdate` 把状态设为 `in_progress`  
4. `TaskGet` 取完整上下文，执行具体工作  
5. 完成后 `TaskUpdate` → `completed`；若有新工作再 `TaskCreate`  

状态流转：

```text
pending → in_progress → completed
                          （或）
                      ↘ deleted（任意状态都可硬删除，不是 Task.state 的持久取值）
```

## 3. `_agent_state` 是干什么的？（当时的疑惑）

一开始会问：一定要维持这么一个 `_agent_state` 吗？它存了什么？

结论：

- `_agent_state` **不是**任务对象自己的字段  
- 它是告诉工具：**改的是哪一个 Agent、哪一份会话里的任务清单**  
- 准确说：在 `agent.state.tasks_context` 里找到任务 X，再改状态 / 阻塞关系等  

`TaskUpdate()` 单独 `new` 出来只是工具对象；真正执行时还要知道：

- 当前是哪个 Agent？  
- 会话状态是什么？  
- 清单里有哪些任务？  

这些都在 `AgentState` 里。框架在 `is_state_injected=True` 时自动注入 `_agent_state=agent.state`，所以 Agent 正常跑工具时不用手写；**手动直接调工具**时才需要显式传入，例如：

```python
await TaskUpdate().call(
    task_id="1",
    add_blocked_by=["2"],
    _agent_state=agent.state,
)
```

## 4. 状态存在哪：AgentState → TaskContext → Task

```text
AgentState
├── session_id
├── summary
├── context
├── permission_context
├── tool_context
├── tasks_context          ← 计划清单在这里
│     └── tasks: list[Task]
└── middle_context
```

```python
class Task(BaseModel):
    id: str                       # 单调递增数字串，由 TaskCreate 分配
    subject: str                  # 一句话命令式描述
    description: str              # 详细需求 / 上下文
    state: Literal["pending", "in_progress", "completed"] = "pending"
    owner: str | None = None
    blocks: list[str] = []        # 被本任务阻塞的任务 ID
    blocked_by: list[str] = []    # 阻塞本任务的任务 ID
    metadata: dict[str, Any] = {}
    created_at: str               # ISO-8601


class TaskContext(BaseModel):
    tasks: list[Task] = []
```

理清「工具改的是 state 里的清单」之后，后面就比较顺了。

## 5. 谁决定创建任务？

| 模式 | 流程 |
|------|------|
| **常规 Agent** | 模型决定 → Toolkit 调用 `TaskCreate` → 写入 `tasks_context` |
| **手动控制** | 开发者直接调用 `TaskCreate`（并注入 `_agent_state`）→ 创建任务 |

可以记：

- `AgentState`：保存任务  
- `TaskCreate` 等工具：真正增删改查  
- 常规执行里「创不创建、创什么」，通常由模型根据指令和工具描述决定；Toolkit 负责注入当前状态并执行  

## 6. 自定义 / 绕过 LLM 管理任务

任务存在 `agent.state.tasks_context`，开发者可以**不经过模型**直接改清单。常见场景：

| 场景 | 一句话 |
|------|--------|
| **Seeding（预置）** | 用外部方案初始化一份新计划 |
| **Importing（导入）** | 把外部正式工单映射进 Agent 的任务 |
| **Migrating（迁移）** | 把已有 Agent 工作状态转移或恢复 |
| **Evaluation（评测）** | 推理前由测试 harness 注入 ground-truth 任务 |

三者并不完全一样；严格区分可以等真实项目里用到再抠。现阶段先记住：**计划数据在 state 里，既可以让模型维护，也可以由代码直接喂。**

## 7. 和「确定性工作流」的边界（通用）

Plan 适合记录「要做哪些步骤、做到哪了、谁阻塞谁」。  
但强业务规则（必须审批、状态只能按固定流转等）仍应由工作流 / 业务服务强制执行——**Plan 是可观察清单，不是硬锁状态机。**  
依赖边（`blocks` / `blocked_by`）偏建议与规划，默认不会像数据库约束那样强制拦住执行。
